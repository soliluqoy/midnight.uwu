# Vault needs measured gates before implementation

This records the prebuild audit. Subsequent physical-device work is tracked in
the [Phase 0 record](../docs/spikes/phase0-2026-10-18/README.md) and
[ADR 0002](../docs/adr/0002-phase0-native-findings.md); its passing probes do not
establish completion of Phase 0. Historical installation counts below refer to
the [preserved prebuild JSON](../docs/ops/prebuild-toolchain-verification.json).

**The Android and Windows development baseline now passes installation checks and empty-template native builds, but Vault's product feasibility remains unproven.** An actual Android smoke build exposed a missing exact NDK revision despite healthy Flutter doctor and installed-file checks; the missing toolchain is installed and the APK build now passes. The audit also found design defects: the plan exposed its grant-minting secret to viewers, specified the wrong Ed25519 signature length, weakened direct-only media with TURN, assumed a Windows player backend that the chosen package does not provide, and treated Android background scheduling as continuous availability. The authoritative plan, workspace configuration and verification scripts have been corrected before feature work. Empty-template builds do not validate the future WebRTC/player dependency graph or any Vault outcome. The next step is a bounded, evidence-producing Phase 0, with authenticated direct-range VOD as its first product hypothesis and live fan-out as a separate decision. Global discovery, hardware encoding, background hosting, throughput, battery use and six-viewer capacity remain unproven.

## Owner-controlled viewing is the product's central promise

Vault's intended product is a personal media library published from an Android or Windows device, with local identities, explicit owner approval and media delivered directly to approved viewers. The repository postpones viewer cache re-sharing until a later phase, so the initial topology is one owner serving several independent viewers rather than a decentralized swarm. Its first useful end-to-end experience is straightforward: select a supported local folder, establish and verify a peer identity, approve a narrowly scoped request, browse authorized metadata, then play and seek without first downloading the whole file. Optional public listing and interchangeable signaling transports help peers rendezvous; they are dependencies around that experience, rather than the experience itself. ([Build plan](../P2P_VIDEO_SHARE_BUILD_PLAN.md), [Research scope and evidence](../research_notes/Vault%20prebuild%20architecture%20audit/media.md))

Three limits follow from those choices. An uncached library is available only while its publishing device is executing, permitted to access storage and reachable. STUN discovers addresses but is not a complete NAT traversal solution, and manually exchanging SDP cannot create a route that the networks do not permit. TURN would forward media through another party, even when encrypted, so it contradicts the existing direct-only promise and belongs outside v1 unless that product constraint is deliberately changed. The honest failure state is that no direct route was established; it should not assert a particular NAT diagnosis without evidence. ([STUN, RFC 8489](https://www.rfc-editor.org/rfc/rfc8489.html), [ICE, RFC 8445](https://www.rfc-editor.org/rfc/rfc8445.html#section-2), [TURN, RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html#section-1))

Likewise, consent can govern **future delivery**, not erase a viewer's already delivered, buffered, saved or captured bytes. Offline caching and downloading make that boundary especially important. Revocation therefore means persisting the owner's decision, refusing further protected reads, cancelling queued work and closing affected sessions; a remote notification is additional feedback, not the enforcement mechanism. That interpretation preserves the product's useful ownership model without making an impossible deletion promise. ([Capability and revocation audit](../research_notes/Vault%20prebuild%20architecture%20audit/protocol.md), [HMAC, RFC 2104](https://www.rfc-editor.org/rfc/rfc2104.html))

## Cryptographic authority must stay with the owner

The most consequential security finding was the proposed `ACCESS_RESULT` returning the same `streamSecret` used to mint HMAC capabilities. **A viewer given that secret can calculate additional valid MACs.** The corrected design must retain the minting secret only on the owner and return a scoped grant/MAC, bound to the authenticated viewer, resource, actions, expiry and persisted authorization epoch. Every protected metadata, poster, manifest, byte-range or live-track request must check those conditions and the current revoked/blocked state before delivery. The full ACL remains local. This is a necessary correction to the plan, not an implemented authorization system. ([HMAC construction, RFC 2104](https://www.rfc-editor.org/rfc/rfc2104.html), [Proof-of-possession and replay principles, RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html#section-11))

The wire format also needs one frozen, deterministic profile and interoperability fixtures before packages implement it. Ed25519 public keys are **32 bytes** and signatures are **64 bytes**. A signature must cover a domain-separated, unambiguous encoding of the complete relevant header and body, including recipient/scope, message/session identifiers, expiry and negotiation generation. Duplicate-key rejection, size/depth bounds and replay caches are part of the protocol contract. A self-asserted node ID in a DataChannel greeting does not prove identity; the peer must prove possession of the expected key and bind that proof to the actual session and SDP fingerprints before receiving private material. A reinstall with a new key consequently creates a new identity and requires fresh approval. ([Ed25519, RFC 8032](https://www.rfc-editor.org/rfc/rfc8032), [Deterministic CBOR, RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2), [WebRTC security architecture, RFC 8827](https://www.rfc-editor.org/rfc/rfc8827.html))

Public signaling must carry authenticated, end-to-end encrypted addressed negotiations rather than merely signed clear SDP and ICE candidates; signatures alone do not hide network addresses. The exact encryption construction and validated library remain an ADR and test-vector gate. Nostr is a distinct optional transport integration: NIP-01 uses Schnorr/secp256k1 keys and JSON outer events, while NIP-44 specifies a particular encryption construction rather than a general “NIP-44-style” recipe for Ed25519 keys. If retained, Nostr needs its own transport key bound to Vault's identity and exact conformance tests. ([ICE privacy considerations](https://www.rfc-editor.org/rfc/rfc8445.html#section-19.1), [HPKE specification](https://www.rfc-editor.org/rfc/rfc9180.html), [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md), [NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md))

Public discovery should begin as an explicitly opted-in, bounded pilot. Hashing publisher IDs into shards does not tell a text search which shard contains a matching name, and connecting to several brokers does not make them federated. The defensible initial design searches a bounded local cache of valid live announcements on shared endpoints, expires records by the publisher's signed lifetime and reports partial results. It must exclude filenames, posters, paths, ACLs, tokens and IP hints. EMQX and Mosquitto document public/test services with visibility or reliability limitations; TLS and `retain=false` do not promise secrecy or absence of logging. Endpoint handshake, publish/subscribe behavior, outages, duplicates, replay and abuse limits need measurement before any discovery SLA is claimed. ([EMQX public broker](https://www.emqx.com/en/mqtt/public-mqtt5-broker), [Mosquitto test service](https://test.mosquitto.org/), [MQTT 5 specification](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html), [Directory design findings](../research_notes/Vault%20prebuild%20architecture%20audit/protocol.md))

## Random-access VOD must work before live fan-out scales

The transport needs distinct reliable ordered channels for critical control and bulk data, with an optional lossy channel reserved for disposable peer stats. A lost revocation notice cannot be the only consent mechanism. The **256 KiB integrity/cache chunk is not a DataChannel message size**: application fragments should fit a conservative 16 KiB envelope and any smaller negotiated finite maximum, with bounded reassembly and authenticated chunk digests tied to a content generation. Channel separation does not remove their shared SCTP congestion control. Backpressure must poll the native value through `await getBufferedAmount()`, account for locally queued serialized bytes and handle errors/teardown; repeatedly reading the cached `bufferedAmount` property is not the documented workaround. The relevant desktop reports are #2206 for buffered-amount notifications and #2210 for encoding changes, rather than the plan's unrelated issue references. ([DataChannels, RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html), [Maximum message size, RFC 8841](https://www.rfc-editor.org/rfc/rfc8841.html#section-6.1), [Pinned plugin implementation](https://raw.githubusercontent.com/flutter-webrtc/flutter-webrtc/v1.6.2%2Bhotfix.4/lib/src/native/rtc_data_channel_impl.dart), [Issue #2206](https://github.com/flutter-webrtc/flutter-webrtc/issues/2206), [Issue #2210](https://github.com/flutter-webrtc/flutter-webrtc/issues/2210))

Transported bytes are useful only if a player can request them correctly. The standard Flutter `video_player` package does not supply Windows support, while media_kit is a candidate requiring its complete native dependency set and a proven adapter. MP4 can place its index at the tail, and accurate seeking can require decoding from an earlier keyframe; a sequential growing file cannot by itself establish arbitrary seeking. The spike must handle front/tail metadata, cold-cache nonsequential seeks, cancellation, audio, unsupported formats and EOF without presenting unavailable sparse-file holes as valid bytes. A loopback-only HTTP Range adapter is one possible integration, provided it implements real range semantics and session access/lifetime controls; native player data-source integration is another. Neither choice is already implemented. ([Flutter playback guidance](https://docs.flutter.dev/cookbook/plugins/play-video), [media_kit project](https://github.com/media-kit/media-kit/blob/main/README.md), [MP4 faststart behavior](https://www.ffmpeg.org/ffmpeg-formats.html#mov_002c-mp4_002c-ismv), [Android seek behavior](https://developer.android.com/media/media3/exoplayer/troubleshooting#why-is-seeking-in-my-video-slow), [HTTP ranges, RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-range))

Android storage adds a separate capability boundary. SAF supplies document/tree URIs, not universal filesystem paths; permissions can be lost and read descriptors need not be seekable. Storage must expose capability-aware range reads and an explicit rejection or user-approved staging policy for unsupported providers. Indexing should make enumeration browseable before full hashes and posters complete. The plan's 1 MiB prefix hash for 20,000 files alone reads up to **19.53 GiB**, implying **333.3 MiB/s** to finish in 60 seconds before provider, metadata, thumbnail or database work; that is arithmetic from the proposed workload, not a measured device result. Android/Windows thumbnail APIs also do not establish an exact frame-at-22%-duration guarantee. ([SAF guide](https://developer.android.com/training/data-storage/shared/documents-files), [ContentResolver](https://developer.android.com/reference/android/content/ContentResolver), [Android thumbnail API](https://developer.android.com/reference/android/media/MediaMetadataRetriever), [Windows thumbnail API](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishellitemimagefactory-getimage), [Indexing analysis](../research_notes/Vault%20prebuild%20architecture%20audit/platform.md))

Live mode needs its own video-and-audio file ingestion, timestamp, encoder and fan-out proof. A shared raw track does not demonstrate one shared encoded frame stream across independent peer connections, and arbitrary independent VOD timelines cannot share one universal live timeline. Hardware acceleration, session capacity, fallback CPU use and thermal stability must be observed on named devices. The existing six-high-viewer target also fails its own budget: `(2.5 + 0.096) × 1.17 × 6 = 18.22392 Mbps`, exceeding the **14 Mbps** allowed by a 70% cap on a 20-Mbps uplink. The provisional arithmetic permits at most four high viewers before additional costs; six is a maximum session count to test with valid allocation, not a quality guarantee. A 4× downscale from 1280×720 is 320×180, not 426×240, and sending all simulcast layers must charge all their bytes. VOD preserves the source bitrate and cannot inherit live quality switching without alternate renditions or transcoding. ([Encoding parameter semantics](https://www.w3.org/TR/webrtc/#dom-rtcrtpencodingparameters), [Android hardware encoder selection](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/api/org/webrtc/HardwareVideoEncoderFactory.java), [Native factory source](https://raw.githubusercontent.com/webrtc-sdk/libwebrtc/main/src/rtc_peerconnection_factory_impl.cc), [Budget and fan-out audit](../research_notes/Vault%20prebuild%20architecture%20audit/media.md))

## Physical-device and network gates determine the next commitment

Android cannot yet be described as an always-on personal server. For apps targeting Android 15+, background `dataSync` and `mediaProcessing` foreground services each have a six-hour-per-24-hour budget. WorkManager periodic work is inexact, and Doze suspends network access and defers its jobs. A periodic task therefore cannot guarantee MQTT presence or a fixed background folder freshness interval. The next spike must establish valid service types for active transfers and idle publication separately, preserve state, expose availability honestly and respect user stopping. Screen-off, forced Doze, process death, restart, permission loss and budget exhaustion require a physical Android 15/16 device with the actual target SDK and battery configuration recorded. At the prebuild audit, no authorized physical Android device was attached; emulator boot or SDK installation cannot establish these outcomes. ([Foreground service timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout), [Service types](https://developer.android.com/develop/background-work/services/fgs/service-types), [Doze](https://developer.android.com/training/monitoring-device-state/doze-standby), [Periodic work](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest), [User stop behavior](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping))

Phase 0 should produce concrete pass/fail/blocked evidence in dependency order: exact-plugin Android and Windows native builds; frozen protocol and cryptographic golden vectors; authenticated one-to-one control/bulk transfer with bounded queues, adversarial grant/replay/revocation cases and non-relayed ICE verification; a real range-fed VOD player with seek and audio fixtures; then direct-path topology and Android lifecycle runs. Live ingestion, encoder selection, rate changes and 1/2/4/up-to-6-viewer cost follow as a separate go/no-go. A failed live experiment need not invalidate a proven VOD core, but it must change the live scope before feature work relies on it. ([Proposed gate sequence and evidence gaps](../research_notes/Vault%20prebuild%20architecture%20audit/media.md), [Authorization fixtures](../research_notes/Vault%20prebuild%20architecture%20audit/protocol.md))

Network tooling must also be calibrated rather than merely located. The clumsy 0.3 launcher needs documented lag/drop flags, an explicit peer-scoped filter and finite timeout; its throttle module is not a bitrate shaper, and even its bandwidth module drops over-budget packets rather than pacing a link. WSL `tc` can support controlled impairment, but a functioning command or isolated netem probe is not the proposed Pion interoperability/NAT harness. Record the actual topology, mapping/filter rules, rate, added delay/loss, content, cache state and hardware, then collect latency percentiles, steady-state memory, CPU, temperature and real bytes. Public endpoint behavior still needs application-level MQTT/relay checks; port reachability is insufficient. ([clumsy manual](https://jagt.github.io/clumsy/manual.html), [clumsy 0.3 throttle source](https://raw.githubusercontent.com/jagt/clumsy/0.3/src/throttle.c), [bandwidth implementation](https://raw.githubusercontent.com/jagt/clumsy/0.3/src/bandwidth.c), [Network audit](../research_notes/Vault%20prebuild%20architecture%20audit/media.md))

## Conclusion

The largest prebuild risk has shifted from installing executables to proving that the platform and protocol can preserve the intended consent model along a useful playback path. Keep the next commitment small enough to yield decisive evidence: an approved peer obtains authenticated ranges, seeks and hears audio, while a revoked peer cannot obtain another protected range. That result, supported by real lifecycle and direct-route limits, is the foundation on which discovery, richer live modes and higher viewer counts can be judged. **A clean tool audit authorizes feasibility work; it does not certify the product promises.**
