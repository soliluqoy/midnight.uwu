# Vault protocol, discovery, identity, consent, and trust audit

Research date: 2026-10-18. Scope: the local build plan and the protocol, identity, directory, signaling, net, and root README stubs. These are design notes, not implementation or measured feasibility results. Repository observations refer to [the build plan](../../P2P_VIDEO_SHARE_BUILD_PLAN.md) and [root README](../../README.md). No ADRs currently exist under `docs/adr`.

## What identity and wire protocol actually satisfy the intention?

### Takeaway

The intended product is a device-owned media library with bilateral consent, stable local identities, and replaceable untrusted rendezvous transports. Several cryptographic instructions would defeat that intention: the signature length is wrong, the HMAC minting secret is sent to viewers, and the proposed Nostr key type is incompatible with Nostr.

### Cited Findings

- **Confirmed blocker — signature length.** Section 5 specifies a 32-byte Ed25519 signature. Ed25519 public keys are 32 octets, but signatures are 64 octets. The RFC supplies test vectors suitable for interoperability fixtures. — [RFC 8032, §§5.1 and 7.1](https://www.rfc-editor.org/rfc/rfc8032)
- **Confirmed blocker — Nostr keys.** NIP-01 requires Schnorr signatures over secp256k1, not Ed25519, and its wire events are JSON. Ephemeral kinds occupy `20000 <= kind < 30000`; non-storage is a relay convention, not an enforceable confidentiality/deletion promise. Therefore “signed with the device identity key” and “all messages not JSON” cannot apply literally to native Nostr events. — [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md)
- **Confirmed blocker — unspecified “NIP-44-style” encryption.** NIP-44 v2 specifically uses secp256k1 ECDH, HKDF, ChaCha20, HMAC-SHA256, and a signed NIP-01 event. It explicitly lacks forward secrecy and metadata hiding. It is not an interchangeable encryption recipe for Ed25519/X25519 keys. — [NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md)
- **Confirmed protocol ambiguity — encoding.** The plan allows CBOR or MessagePack; the protocol README already promises MessagePack. CBOR has a defined deterministic encoding baseline, while duplicate-map-key handling can differ between decoders. A signature protocol needs one exact representation and rejection policy, rather than “canonical payload” without a definition. — [RFC 8949, §§4.2 and 5.3](https://www.rfc-editor.org/rfc/rfc8949.html)
- **Missing replay protection.** A nonce field plus ±120-second timestamp validation does not specify how duplicate valid messages are rejected. RFC 9449 illustrates the general principle: time-limited signed proofs also need unique-ID tracking during their accepted lifetime, with storage limits. This is a security-design analogy; Vault should not add OAuth or an authorization server. — [RFC 9449, §11.1](https://www.rfc-editor.org/rfc/rfc9449.html#section-11.1)
- **Missing channel-to-identity binding.** WebRTC's security architecture binds identity to SDP certificate fingerprints. Vault does not need its account/IdP model, but must preserve that binding using its own verified device signatures and peer authentication; a bare `DC_HELLO {nodeId}` string is not proof of key possession. — [RFC 8827, §§5.1.1 and 7.4](https://www.rfc-editor.org/rfc/rfc8827.html)
- **Missing MQTT confidentiality.** ICE warns that exchanged candidates reveal addresses to anyone who can observe negotiation. Signing clear candidates/SDP provides authenticity, not confidentiality. — [RFC 8445, §19.1](https://www.rfc-editor.org/rfc/rfc8445.html#section-19.1)
- HPKE specifies standardized public-key encryption combinations, including X25519-based KEMs. This is a candidate for a researched signaling-encryption ADR, not evidence that a particular Dart package or plugin supports it. — [RFC 9180, §§4 and 7](https://www.rfc-editor.org/rfc/rfc9180.html)

### Inferences

- **Proposed replacement for §5 opening:** “Vault v1 has one frozen deterministic wire profile, recorded with golden vectors before Phase 1. The inner Vault envelope uses deterministic CBOR per RFC 8949 §4.2.1 (or one fully specified MessagePack profile selected by ADR; never both in the same version), a 1-byte protocol version, a 2-byte message type, a 32-byte Ed25519 public key and a 64-byte Ed25519 signature. Sign a domain-separated encoding of the complete header and body, excluding only the signature. Include sender, intended recipient or broadcast scope, message ID, session ID, issue time, expiry, and ICE generation where relevant. Derive/verify node ID from the supplied public key. Reject duplicate keys, excess nesting/lengths, invalid types, unsupported versions, altered headers, and invalid signatures before acting.” This chooses the exact protocol rather than assuming codec round trips imply canonical signatures. Update the README if CBOR is selected.
- **Proposed replay rule:** “Deduplicate the same authenticated message across all brokers and strategies using `(senderKey, messageId)` through its signed acceptance window. Apply bounded per-peer and total caches; persist replay state needed for grants or use owner-maintained grant epochs that survive restart. Check recipient, session, ICE generation, and expiry before state transitions. Duplicate offers, answers, approvals, and revocations are idempotent. A relayed/gossiped copy cannot extend its origin-signed expiry. Time skew produces a clear diagnostic; it does not disable replay checks.”
- **Proposed signaling confidentiality rule:** “Treat every public broker/relay and every other subscriber as untrusted. Public directory records may be clear only after the publisher explicitly opts in. Addressed offers, answers, candidates, access messages, and tokens are end-to-end encrypted to a recipient encryption key cryptographically bound to that recipient's verified Ed25519 identity. Select the encryption construction and validated implementation in a Phase 0 ADR, including test vectors, size limits, and key rotation. Do not invent a ‘NIP-44-style’ scheme.”
- **Proposed Nostr wording:** “Nostr is an optional transport adapter gated on Phase 0 feasibility. It uses a separate locally stored secp256k1 transport key and NIP-01 outer event, carrying the signed Vault envelope. Bind that transport key to the Vault Ed25519 identity with a signed binding. If NIP-44 is used, implement the exact selected version and vectors with the required Nostr keys. Native Nostr JSON wrapping is permitted; the inner Vault protocol remains binary. Do not claim ephemeral delivery prevents relay logging.”
- **Proposed session authentication rule:** “Before any protected index, manifest, thumbnail, file range, or live track, verify the peer's signature over a fresh challenge and the negotiated session/fingerprints, and bind all authorization to that authenticated peer. Signed offers/answers include their complete SDP and the intended peer/session; candidates are scoped to that negotiation. QR verification establishes the expected identity key; display names are untrusted labels.”
- A reinstall without key restoration creates a new cryptographic identity. Replace success criterion “the host never notices” with: “No server state is required; a preserved/restored identity retains its grants, and a fresh identity requires fresh owner approval.” The current plan's own identity definition implies this result.

### Gaps

- No selected deterministic encoding profile, node-ID encoding, replay persistence strategy, time-skew behavior, key-store ADR, key-backup policy, or verified signaling-encryption library currently exists in the inspected stubs. These remain required design outputs, not installed-tool failures.
- Native libwebrtc mDNS behavior and the chosen Flutter adapter's access to verified fingerprints require actual spikes. Browser defaults do not establish native plugin behavior.

## Can the proposed public directory reliably and privately discover publishers?

### Takeaway

The public transports can carry small signed announcements, but the proposed text-search sharding and epidemic gateway scheme do not establish a scalable federated directory or a 60-second global search guarantee. Use a bounded, explicitly public pilot directory and keep global discovery a measured feasibility gate.

### Cited Findings

- **Public means public.** EMQX advertises its endpoint for prototyping/testing and warns all messages are visible to other users. Its documented WSS endpoint is port 8084, path `/mqtt`, matching the plan. TLS protects the connection to the broker, not payload secrecy from broker subscribers. — [EMQX public broker documentation](https://www.emqx.com/en/mqtt/public-mqtt5-broker)
- Mosquitto lists unauthenticated encrypted WebSockets on 8081. Anonymous users can publish all topics and subscribe to nearly all topics; its operator says not to rely on it for important work and warns WebSocket/TLS support may be unavailable during testing. It explicitly warns against sensitive payloads. — [test.mosquitto.org operator documentation](https://test.mosquitto.org/)
- **Transport redundancy causes duplicates.** MQTT QoS 1 is at-least-once delivery. MQTT retained messages are separate from ordinary publish delivery; retain=false prevents storage as a retained message, but does not constitute a broker-logging privacy guarantee. MQTT 5 also provides retained-message subscription controls. — [MQTT 5.0, §§3.3.1.3 and 4.3.2](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)
- Nostr relays may reject events for restrictions, proof-of-work policy, stale/future time, or no subscriber for an ephemeral event. Publicly reachable does not imply universal acceptance, federation, or delivery guarantees. — [NIP-01 relay responses](https://github.com/nostr-protocol/nips/blob/master/01.md)
- The local plan hashes `nodeId + epoch` to a presence shard but claims one shard can answer a text query, broadcasts all queries on one global topic, calls endpoint redundancy federation, and simultaneously specifies 200 gossip records and a wire cap of 32. These are internal contradictions visible in [§§2.4, 5.2, and Appendix B of the plan](../../P2P_VIDEO_SHARE_BUILD_PLAN.md).

### Inferences

- A uniformly hashed node-ID shard has no relationship to a display-name/tag term. A searcher cannot derive “the shard of the query” without a term index or scanning all owner shards. The 30,000-record bound has no supporting population, message-size, or rate argument. A global query topic also defeats the claimed per-shard load bound.
- A fresh client subscribed to a functioning live topic can hear the next heartbeat without existing peers. “Zero peers means hear nothing” applies to a pure gossip overlay, not pub/sub with known brokers. “Beacon topics” are names, not bootstrap participants; inventing a topic cannot create a seed node.
- MQTT brokers and Nostr relays do not become federated merely because the client connects to several. Peers must share an endpoint/subscription or the application must explicitly and safely bridge messages. Autonomous rebroadcast needs bounded hops, IDs, deduplication, authenticity, and per-source/global limits; otherwise it amplifies spam and loops.
- A small dictionary of likely names/tags can be tested against a query Bloom filter. Treat it as public query metadata rather than a privacy feature. Stable public identity, tags, activity time and item counts also form a public metadata trail. mDNS does not solve that problem.
- Device key generation is free, so signatures do not stop Sybil spam. Bound unauthenticated connection attempts, prompts per owner/time, payload bytes, signature-verification work, directory entries, response fan-out, gossip TTL/hops, and total relay bytes. Do not repeatedly prompt an owner because an attacker rotates keys.
- **Proposed replacement for §2.4:** “Directory search is best effort over the live public endpoints the peers share. Publishing to the public directory is an explicit opt-in; show exactly which name/tags/counts become public. Share no filenames, thumbnails, path names, ACLs, IP hints, grants or tokens in directory records. For the pilot, subscribe to the complete bounded presence namespace, cache valid signed announcements for at most their origin-signed expiry, and search that local cache. Enforce entry/byte/rate limits and report partial results when limits or relay failures apply. Direct QR/contact connection works without public listing. Sharding, cross-endpoint forwarding, and query Bloom filters are later feasibility work; no global completeness or fixed discovery SLA is promised until measured under a documented population/load.”
- Preserve the 30s heartbeat, 90s expiry and 15s sweep as provisional tunable pilot values. Use a monotonically newer publisher sequence within an origin epoch to reject older records; only the publisher may issue a newer heartbeat. A copy arriving through gossip never makes an old owner appear online again.
- **Proposed test replacement:** “In the documented 10-node pilot with at least one common reachable broker, a new node discovers at least 8/10 online opt-in publishers in 60s. Also test disconnected broker islands, duplicate deliveries, expired-record replay, gateway loss, bounded spam, cold start, and relay outage. Passing the small test is not evidence of Internet-scale discovery.”
- Make gossip wire batches consistently `<=32` records; a 200-record exchange is multiple bounded batches subject to a byte/rate budget, if gossip is retained.

### Gaps

- No live endpoint permission or reliability SLA was established; no production guarantee should be inferred from successful TCP/TLS/WebSocket connection.
- The third Eclipse broker path in the original plan was not independently verified in this subtask; parent/toolchain audit should check documentation and real MQTT CONNACK/SUBACK/PUBACK, rather than only port reachability.
- There is no measured distribution, rate budget, abuse model, cross-relay routing protocol or large-scale directory benchmark. The proposed user experience is feasible only as a scoped hypothesis until those are supplied.

## How should capabilities, revocation, and the direct-only constraint be corrected?

### Takeaway

Keep the capability-minting secret solely with the owner and bind each grant to an authenticated viewer. Revocation can stop future delivery promptly, but cannot erase media already received. The strongest existing product constraint is direct-only media, so optional TURN must be removed from v1 rather than silently weakening that promise.

### Cited Findings

- **Critical authorization failure.** HMAC uses the same secret key to calculate and verify a MAC. The plan both uses a per-installation `streamSecret` to mint capabilities and returns it in `ACCESS_RESULT`; any granted viewer receiving that secret can calculate fresh MACs. — [RFC 2104, §§1–2](https://www.rfc-editor.org/rfc/rfc2104.html)
- Signed proof-of-possession tokens require verification that the presenter controls the key to which a token is bound; freshness and replay checks are additional requirements. This supplies a design precedent without requiring Vault to adopt OAuth. — [RFC 9449, §§4 and 11](https://www.rfc-editor.org/rfc/rfc9449.html)
- TURN explicitly relays application packets between peers. Encrypting those packets does not prevent third-party transit. This directly contradicts the plan's hard “never through a third party” media rule while optional TURN is configured. — [RFC 8656, §§2 and 21.2](https://www.rfc-editor.org/rfc/rfc8656.html)
- Manual signaling carries candidate addresses and descriptions; ICE still performs connectivity checks and requires a viable network path. Exchanging an offer by QR does not itself create connectivity through an unreachable network. — [RFC 8445, §2](https://www.rfc-editor.org/rfc/rfc8445.html#section-2)
- The local plan deliberately caches media and offers “Save offline” and full download, while promising revocation makes a stream impossible to resume. Those requirements need an explicit already-received-content exception. — [Plan §§5.3, 6.5, and 11](../../P2P_VIDEO_SHARE_BUILD_PLAN.md)

### Inferences

- **Proposed replacement for §2.5:** “The owner keeps a random per-installation HMAC key in protected local storage and never transmits it. A grant contains version, owner ID, authenticated viewer ID, grant ID, exact resource scope, actions/level, issuedAt, expiresAt, and a persisted owner-controlled authorization epoch; its MAC covers an unambiguous canonical encoding and an explicit domain label. `ACCESS_RESULT` returns the grant and MAC only, never the minting secret or full ACL. On every protected request the owner checks the MAC, authenticated viewer identity, scope, expiry, current epoch and local revoked/blocked state before reading/sending bytes. This is an owner-verifiable capability; future viewer-to-viewer re-sharing needs a separately researched delegation design.”
- Replace `ACCESS_RESULT {allowed, token, expiresAt, streamSecret, acl}` with `{allowed, grant?, expiresAt?, reason?}`. Keep the complete ACL local; approved viewers learn only their own grant/permissions. Remove `lastSeenIpHint` from distributed records. Do not leak other viewers' identities in a full ACL.
- Bind tokens to the authenticated viewer, not a self-asserted nodeId. Add explicit authorization states: unauthenticated, authenticated/no grant, approved, revoked, blocked. Pre-approval allows only a strictly bounded handshake/access request, never private index, metadata, posters, ranges or media tracks. The public directory may disclose only the explicitly opted-in fields.
- Persist revocations and block decisions. Revoking a grant invalidates it before any closure attempt, cancels reads and queued sends, prevents reconnect/resume and closes affected PeerConnections. Test old token reuse after process restart, key rotation, reconnect and attempted downgrade, not only immediate connection closure.
- **Proposed revocation language:** “Within 1s of the owner's action, stop scheduling new protected bytes and close the affected sessions; reject future requests with revoked grants, including after restart. Already transmitted, buffered, cached, saved or captured media cannot be recalled. Viewer-side disconnect likewise stops further transfer and prevents automatic reconnect until explicitly allowed.” No network design can make a recipient forget bytes it already possesses.
- A remote `REVOKE` notice is informational; owner-side state is authoritative and must work if the notice is lost. Consent-critical commands/acknowledgments belong on a reliable ordered control channel or require explicit acknowledgment/retry/idempotency. `maxRetransmits:0` is appropriate for disposable stats, not the only delivery path for permissions and session control.
- **Proposed direct-only replacement:** “v1 configures STUN only and never accepts or supplies TURN. Reject relay ICE candidates and assert the selected candidate pair is not relayed before and throughout protected transfer. If no direct path exists, report that the networks cannot connect directly and suggest a reachable LAN/network path or Manual signaling only when relay signaling itself is the issue. A future optional user-supplied TURN mode requires an explicit product decision changing the direct-only guarantee and cannot be enabled under the current constraint.” Remove TURN from settings, candidate preferences, NAT help, risk mitigation and Phase 7 claims unless that product decision is made.
- **Proposed Manual wording:** “ManualSignaling exchanges the complete compressed offer and answer using text or bounded multi-part QR, after candidate gathering. A short code/safety phrase verifies an identity or transcript; without a rendezvous/storage service it cannot stand in for an arbitrary full SDP blob. This removes signaling infrastructure, not ICE/network requirements; it works on a reachable LAN or another viable direct path, not disconnected air-gapped peers.”
- A signaling byte budget alone cannot prove zero media bytes: a small thumbnail fits under that budget. Use typed payload allowlists and tests rejecting media/thumbnail/file message kinds at the signaling boundary, then verify direct ICE selection and actual transfer paths separately. Restrict signals to the schema and size/rate limits; avoid arbitrary binary fields that can smuggle content.

### Gaps

- An honest `<1s` DoD needs a defined observation boundary: owner scheduling stop, transport close and viewer UI notification are distinct events under latency/loss. Measure all three; the owner can immediately enforce future access locally without promising an impossible global receipt deadline.
- No adversarial authorization tests exist yet. Required fixtures include a valid viewer trying to mint a different resource grant, copied tokens presented by another identity, modified scopes, expired tokens, replayed approval, revoked grant after restart, blocked fresh-session attempts, unauthorized thumbnails/index requests, and old SDP/candidates in a new session.
- Direct-only NAT reachability is an accepted product limitation, not something signing, directory gossip or manual QR can fix. No quantitative public connectability percentage was established here.
